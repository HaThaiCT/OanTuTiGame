# Online v2 delivery design

## Intent and authorization

Implement the existing ON-01–08 backlog on `develop/online-v2`, retaining the LAN engine/ledger/map/submission authority. The user requests autonomous planning, implementation, verification and publication preparation until deployment requires their intervention. Technical decisions below are the implementer's choices derived from the existing security/product specs, not new user commitments. Preserve `release/lan-v2`, `main`, donor workspace, demo database and running demo services. Only the Online branch may be pushed. No tag, GitHub Release, image publication, real email, public listener, provider/account provisioning or public deployment is authorized by this design.

## Software outcome

An ONLINE deployment has strict validated configuration, durable encrypted mail delivery, verified registration/admin bootstrap, recovery and email change, team self-service and shared-code lifecycle, and browser journeys proved on an isolated stack. A LAN deployment continues without SMTP or mail sockets. Software verification is not G0–G4 commissioning, U5 acceptance, capacity certification or a production-ready assertion. ON-08 includes implementable deployment packaging, preflight and operator instructions; actual host/domain/mailbox/provider authorization and evidence remain the human deployment boundary.

## Config and token custody (ON-01)

Reuse Fastify/PostgreSQL/Next.js; add no alternate identity system. Resolve auth profile once, accept only LAN_OFFLINE/ONLINE (unset remains LAN_OFFLINE), reject unknown/empty configured values. ONLINE requires PostgreSQL and exact HTTPS origin `OANTUTI_PUBLIC_BASE_URL`, no userinfo/path/query/fragment/wildcards. Allowed mutation origins equal that origin; proxy trust is an explicit IP/CIDR allowlist, never trust-all. Cookies are Secure in ONLINE independently of forwarded HTTP headers.

Provider-neutral SMTP with verified implicit TLS or required STARTTLS: `OANTUTI_SMTP_HOST`, `OANTUTI_SMTP_PORT`, `OANTUTI_SMTP_TLS_MODE` (implicit/starttls), `OANTUTI_SMTP_USER`, `OANTUTI_SMTP_PASSWORD_FILE`, `OANTUTI_MAIL_FROM`, `OANTUTI_MAIL_REPLY_TO`. Prefer a maintained SMTP library to implementing a protocol parser; pin its exact installed version and types in the lockfile. It must not connect at module import or LAN startup. Internal tests inject a transport instead of enabling external mail. ONLINE production config does not expose a test transport toggle.

`OANTUTI_MAIL_KEYRING_FILE` holds JSON `{currentKeyId, keys:{keyId: base64_32_byte_key}}`, allowing a current encryption key and retained decrypt-only keys. Reject non-regular/symlink/foreign-owned/group-or-world-readable credential files. No secret values in config errors/logs. AES-256-GCM with random 12-byte nonce, version/key ID, authentication tag and AAD binding outbox UUID/topic/user/purpose/token hash. Encrypted material contains recipient and raw token; public outbox metadata contains only identifiers/purpose/expiry, not email/username/token. Passwords remain Argon2id; verification/reset tokens retain random 32-byte hash-only verifier tables. Delete encrypted delivery material on terminal delivery/expiry/cancellation; bounded held failures retain it only until expiry. Key retirement requires draining/re-encrypting outstanding events and operator escrow; never derive keys from passwords/environment defaults. Remove the plaintext dev-token path and migrate tests to injected encrypted delivery. Applied migrations are immutable; add migration 028 for Online identity/delivery and reserve 029 for any team schema needs.

## Durable mail (ON-02)

Reuse `outbox_events` transaction publication; add a mail-only delivery record associated with an outbox ID for ciphertext, attempt count, due time, claim lease and terminal state. Result consumer continues selecting only result topics; mail consumer selects only its own records. Claim using PostgreSQL locking/lease with fencing; restart reclaims expired leases, never loses queued requests. Network send is outside a database transaction. SMTP is at-least-once: a crash after SMTP accept but before receipt can resend the same message; stable Message-ID and one-use token make duplicates harmless, not a claim of exactly-once email.

Before delivery, recheck expiry and current token validity/email binding, suppress rotated/consumed/expired tokens. Serialize identity/token mutation against the delivery eligibility decision where practicable; SMTP cannot revoke already delivered messages and their links must always revalidate at redemption. Timeout delivery below lease lifetime. First failure schedules 15s, second 60s, third 300s; fourth holds and emits redacted structured alert with event ID/reason only. Expired/invalid mail terminates without transport invocation. Drain/stop consumer on app close before DB closes; LAN never creates it. Internal recording transport captures complete messages solely in test memory/private smoke tooling. Production transport never logs SMTP exception strings containing addresses/credentials.

## Identity (ON-03/04/05)

Add explicit `users.email_verified_at` state bound to the current normalized email; do not backfill LAN/self-register records as verified from historical consumed tokens. Every ONLINE login and authenticated actor resolution requires a verified current email. New accounts start pending, no session/team/source access. Verification token stores target address and purpose; consume atomically against user row and update verified state. Never use consumed/inactivated token history as account verification state.

Registration locks account writers with the existing `LOCK TABLE users IN SHARE ROW EXCLUSIVE MODE`, validates configured positive accountCapacity and counts all users, then inserts pending user/token/encrypted outbox together. Duplicate handling remains explicit. Resend accepts email and answers uniformly, rate-limited by hashed account/IP counters (3/account/hour, 20/IP/hour); atomically invalidates previous verification tokens and pending deliveries then queues a new 24-hour token. GET verification pages render only; explicit user POST/button consumes. Expiry points to resend rather than duplicate registration. Links use URL fragments for tokens (client reads fragment after navigation) to keep tokens out of HTTP request logs/referrers; set private no-store/referrer-policy on sensitive panels.

Recovery uses 30-minute tokens, 3/account/hour and 20/IP/hour for known and unknown addresses, deterministic database-clock windows with advisory locks and Retry-After on 429. Uniform accepted body for unknown/known/pending. Reset locks user then token consistently, consumes one token, invalidates sibling reset tokens/deliveries and revokes all sessions atomically. Pending stays pending; no automatic login. Do not print tokens or consider direct DB extraction mail proof.

ONLINE bootstrap is an operator-only command: same singleton users constraint/table lock and capacity/audit transaction, configured email, initial password delivered once via private interactive terminal, pending verification queued durably. No LOCAL_BOOTSTRAP bypass in ONLINE. Existing LAN bootstrap stays LAN-only. Maintenance ONLINE mailbox recovery requires root interactive console, explicit database confirmation, maintenance acknowledgement and nonempty authorization reference/reason; updates the same singleton identity, clears verified state, revokes sessions/all previous tokens, queues verification to authorized new mailbox and issues a new private password. No second ADMIN, no automatic migration, no HTTP recovery authority. Signed organizational authorization is operator evidence, not fabricated by the command.

Email change starts from an existing FULL session with recent reauth <=10 minutes. Verify the new address before replacing current email. Reserve/recheck uniqueness atomically; verification is purpose-bound. On consume, replace email/verified timestamp, revoke sessions and sibling identity tokens, queue notification to old address (no secret or target address in public logs/audit). A stale/duplicate request cannot change identity. Account UI exposes reauth/change and verify completion without silently renewing session.

## Team/admission (ON-06)

Reuse current TeamService/admission/entry-code modules and protocol DTOs; no forked Online team database. Implement missing student creation/invitation/accept/decline/revoke/remove/leave/close/captain transfer and corresponding portal. Enforce verified FULL STUDENT, one team per student per tournament (not per course: multiple course-level teams are allowed), configured maxTeamSize (1–5/default3), maxTeams/capacity atomically and enrollment roster locks on every mutation. Team creation is scoped to a selected registration-open tournament's course and team-size policy; invitation acceptance rechecks that policy. A team roster is immutable once any tournament entry references it, including historical/finalized entries, so no participant/source history changes retroactively; students create a new team for later rosters. Existing admitted teams remain viewable and usable for submissions subject to tournament state. Invitation TTL 48h, one-use, bound to intended recipient user ID; authenticated private inbox supports accept/decline without emailing invitation secrets. Captain may revoke/remove before lock, must transfer to an existing member before leaving; a solo captain may only close an unadmitted team. ADMIN LAN direct roster/enrollment stays separate from ONLINE student admission; direct enroll/bulk routes refuse ONLINE. Shared-code rotate/revoke is FULL ADMIN-only, audited, affects future admission and never deletes existing enrollment; retain hashed verifier and scope/window/capacity checks. One active code revision per tournament; issuance rejects an active predecessor unless explicitly rotated.

All roster/admission mutations acquire one transaction-scoped advisory lock `oantuti:roster-admission` before row locks (tournament then team then user IDs in lexical order). This boring global lock bounds expected school-scale writes and closes cross-team accept/admit/transfer races without forking immutable roster snapshots. Tournament entry creation, bulk enrollment, code redemption, and roster locking participate. Code changes serialize on the tournament row; code redemption enforces actual registration timestamps, roster size/member uniqueness and hashed actor/IP throttling. Code admission records code ID/revision. Lock freeze from entry is deliberate and described to users; no automatic unlocking of historical participants.

## Integration/deployment (ON-07/08)

Unknown/unreachable auth profile fails closed in UI, never defaults to LAN success. Add missing panels using current design system, Vietnamese copy and API error conventions. Verify global origin/CSRF against actual full app, Secure cookie through explicitly trusted proxy, pending-account privacy across all private paths, then browser register -> recorded delivery -> verify -> login -> team -> shared code and recovery/email change. Use isolated arena_*test* DB and private object roots/ports, not demo; build web into a separate dist directory to avoid replacing demo bundle.

Provide Online environment/secret inventory and container/systemd wiring consistent with existing deploy system. Preflight validates config, migration/schema, secret permissions, exact origin/proxy, mail readiness and pending operational proofs without sending real email. Public commissioning remains blocked until named host/domain/provider/mailbox, TLS/DNS, off-host backup/restore, sandbox no-network evidence and operator signoffs exist. No env toggle can assert ONLINE_READY.

## Verification and review

Permanent tests cover consumer-visible boundaries: atomic capacity/membership, token purpose/email/expiry/rotation/revocation, crash/lease/retry/outbox separation, ciphertext tampering/key rotation, redacted failure behavior, profile fail-closed, pending privacy and cookie/origin semantics. Run targeted failures before fixes where existing behavior is wrong. Integrator runs shared isolated tests/typecheck/build once after implementation waves; agents skip mid-flight builds/tests/formatters to prevent shared-state contention. Real private-stack/API/browser smoke is required in addition to tests; record commands/results/skips without secrets. Independent final review focuses security, migrations/isolation, full-app lifecycle and LAN compatibility; resolve blockers, then push Online branch and observe CI at exact SHA. Report deployment prerequisites precisely rather than claiming public release.
